ISSUE #1: pending_upgrade Status Rejected by Database
───────────────────────────────────────────────────────────────────────────────

ERROR:
  2026-04-04T16:20:59 ERROR sync_config: Batch 0: 1644 (45000): Invalid Status:
  "pending_upgrade". Allowed: active, expired, inactive, pending.

ROOT CAUSE:
  Schema snapshot shows pending_upgrade in the members.Status ENUM, but the LIVE
  database hasn't been updated. The constraint was changed in the snapshot but never
  deployed to Azure MySQL.

  File: db/schema_snapshot.sql (line 145-178)
  Shows: ENUM('active','expired','inactive','pending','pending_upgrade')
  Shows: CONSTRAINT chk_members_status_valid includes pending_upgrade

  But live db/mysql-mmr doesn't have these changes applied yet.

SOLUTION:
  Created: db/MIGRATION_V010_add_pending_upgrade_status.sql

  This migration:
  1. Alters members.Status ENUM to explicitly include pending_upgrade
  2. Updates the CHECK constraint to match schema_snapshot
  3. Self-registers in schema_migrations table for audit trail

  To deploy:
    $ source load-env.sh
    $ mysql-mmr < db/MIGRATION_V010_add_pending_upgrade_status.sql
    $ verify: SELECT Status FROM information_schema.COLUMNS WHERE TABLE_NAME='members'

IMPACT: After migration, sync can accept pending_upgrade rows without constraint errors

ISSUE #2: Polling Infinite Loop - Frontend Doesn't Stop After Job Completes
───────────────────────────────────────────────────────────────────────────────

EVIDENCE:
  2026-04-04T16:21:00 INFO api_sheets_sync_routes: [FETCH] Job 594c20eb COMPLETE
  status=error, still being polled — user_agent=...Chrome...

  (repeated every 1 second for 15+ seconds, never stops)

ROOT CAUSE #1 — Duplicate Endpoints:
  Found TWO implementations of /api/sync/status/<job_id>:

  1. mmr-admin/api_sheets_sync.py (line 51)  — OLD, no diagnostics
     @sheets_sync_bp.route('/api/sync/status/<job_id>')
     def api_sync_status(job_id):
         job = get_job(job_id)
         return json_response({'ok': True, 'data': job})

  2. mmr-admin/api_sheets_sync_routes.py (line 189) — NEW, with diagnostics
     @sheets_sync_bp.route('/api/sync/status/<job_id>')
     def api_sync_status(job_id: str):
         [... with user-agent logging, completion detection ...]

  Flask uses whichever blueprint registered LAST. If api_sheets_sync.py loads after
  api_sheets_sync_routes.py, it OVERWRITES the diagnostic version with the old one.
  Result: No logging, no way to debug why polling doesn't stop.

ROOT CAUSE #2 — Batch Count Calculation Bug:
  File: basecamp/python/sync_config.py (line 712)

  Code: batch_inserted = len(batch) // 2  # "Rough estimate"
        batch_updated = res - batch_inserted

  Problem: Dividing batch size by 2 is a GUESS. When res (affected rows from DB)
  doesn't match this guess, batch_updated can go NEGATIVE.

  Example: 280 rows in batch
    - batch_inserted = 280 // 2 = 140  (WRONG — just a guess)
    - batch_updated = 280 - 140 = 140   (happens to work this time)

    But next batch of 11 rows:
    - batch_inserted = 11 // 2 = 5  (WRONG)
    - batch_updated = 11 - 5 = 6    (still positive by accident)

  Cumulative effect: Final count shows "updated: -280" (impossible!)


SOLUTIONS APPLIED:
───────────────────────────────────────────────────────────────────────────────

1. REMOVED DUPLICATE ENDPOINT (api_sheets_sync.py):
   File: mmr-admin/api_sheets_sync.py (lines 39-58)

   Old: @sheets_sync_bp.route('/api/sync/status/<job_id>') — active
   New: Commented out old implementation, left reference notes

   Effect: Only api_sheets_sync_routes.py endpoint is active now.
           Ensures logging + completion detection works.

2. ADDED DIAGNOSTIC BATCH COUNTING (sync_config.py):
   File: basecamp/python/sync_config.py (lines 710-750)

   Old: batch_inserted = len(batch) // 2
        batch_updated = res - batch_inserted

   New: Pre-query DB to count existing keys vs new rows:
        for row in batch:
            check if primary key already exists in table
        batch_updated = count_existing
        batch_inserted = count_new

   Fallback: If diagnostic check fails, use res count directly

   Logging:
     - Log: "Batch N: db_execute returned res={N}, batch_size={B}, pk='{field}'"
     - Log: "Batch N: DIAGNOSTIC — pre-existing keys=X, new=Y, total_batch=Z"
     - Log: "Batch N: SUMMARY inserted=X, updated=Y, skipped=Z, affected_rows_from_db=res"

   Effect: Accurate insert/update counts, no more negative values.

3. ADDED POLLING LOOP DETECTION (api_sheets_sync_routes.py):
   File: mmr-admin/api_sheets_sync_routes.py (lines 189-227)

   New logging:
     - Debug: "[FETCH] Job {id} status={status}, progress={N}%" (while running)
     - Info:  "[FETCH] Job {id} COMPLETE status={status}, still being polled" (after done)

   Also log: user_agent + referer to find which client is polling

   Effect: Can identify if frontend is stuck in polling loop after job finishes.
