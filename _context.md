### 07-30 UTC — Google login: spinner never resolved (client-side, not OAuth config)
Changed: reported symptom was "Continue with Google spins forever, no timeout". Ruled out the server end against prod — provider registered, Google *accepts* the redirect URI (followed the authorize URL to a real sign-in page), the JSON `X-Auth-Return-Redirect` POST returns a valid `{url}`, `/auth/complete` answers in ~0.15s. The hang is the last step of next-auth's `signIn()`: `window.location.href = <google url>`, which never commits when `accounts.google.com` is unreachable (mainland China, or a WeChat/QQ webview refusing the hop) — and `handleOAuth` had **no try/catch and no timeout**, unlike `handleCredentials`. Added a 6s watchdog offering the email+password fallback, a catch for a rejecting `signIn`, and NEW `lib/is-webview.ts` replacing the inline UA check that **omitted WeChat** — Android WeChat reads as ordinary Chrome (`MicroMessenger` + no `; wv)`), so the existing "open in a browser" banner never fired for the club's main sharing channel.
Also fixed: **`/auth/complete` no longer creates members.** An unrecognised OAuth email used to mint a fresh `pending` row and redirect to `/join`, which forked an existing member onto a second MemberID whenever their Google address differed from the one on file — and 130+ active members are on yahoo/hotmail/aol/msn, so mismatch is the norm. It now redirects to `/login?error=oauth_no_member` (**no email in the query string** — that would land in browser history and edge logs) with bilingual copy naming the likely cause and the "Forgot password" route. The `/join` branch is gone (`DEFAULT_DESTINATION`); signing in is not signing up, and `/join` + the admin panel still collect the phone/district/type/payment a social profile can't supply. Verified prod has **0 rows** matching the old auto-create shape (pending + no phone + no WeChat + no payment), so there is nothing to clean up.

WebViewWarning + StallNotice, `messages.ts` 55, `shared.tsx` 38, `GoodbyeBanner` 33) — same `useXFlow` + views shape as `join/`/`donate/`. Extracting the error copy exposed a **real pre-existing i18n bug**: the `?error=` message was seeded in a `useState` initializer, which runs on the first render while `lang` is still the 'en' default (LanguageProvider hydrates from localStorage in an effect AFTER mount) — so a 中文 member got Chinese buttons and an English error, permanently. Verified in a browser: `mmr-lang=zh` renders the whole card in Chinese, error included.
Also fixed: **`?from=` is now honoured, and validated.** The credentials path already sent `/auth/complete?from=<returnTo>` and the route ignored it, so every member was dumped on `/portal` instead of the page they wanted; the OAuth path dropped `from` entirely. Off-site forms (absolute URL, `//evil.com`, `/\evil.com`, `javascript:`, bare relative) and loop targets (`/login`, `/auth/`, `/join`) all fall back to `/portal`.
