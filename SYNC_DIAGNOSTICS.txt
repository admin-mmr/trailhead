SYNC JOB DIAGNOSTICS GUIDE
═══════════════════════════════════════════════════════════════════════════════

PROBLEM: Negative row counts in sync results, fetch job status doesn't stop pinging.

Root Cause Identified: basecamp/python/sync_config.py line 712 uses incorrect math:
  batch_inserted = len(batch) // 2  # WRONG — estimates inserts as half the batch size
  batch_updated = res - batch_inserted  # Can be NEGATIVE!

Example from your logs:
  Processing batch 10 (50 rows) for gmail_transactions
  → res (affected_rows from DB) = 280
  → batch_inserted = 280 // 2 = 140  (WRONG estimate)
  → batch_updated = res - 140 = 140 (happens to be positive by accident)

  But then:
  Processing batch 11 (11 rows) for gmail_transactions
  → res = maybe 11 or less
  → batch_inserted = 11 // 2 = 5 (WRONG)
  → batch_updated = 11 - 5 = 6 (by coincidence positive, but still wrong)

Then final tally shows: "updated: -280" → actual count went negative somewhere.

───────────────────────────────────────────────────────────────────────────────
DIAGNOSTIC LOGS TO WATCH (Added in this session)
───────────────────────────────────────────────────────────────────────────────

1. BATCH PROCESSING LOGS (sync_config.py):

   Level: INFO
   Format: "Batch N: db_execute returned res={N}, batch_size={N}, pk='{field}'"
   Example: "Batch 10: db_execute returned res=280, batch_size=50, pk='MessageId'"

   What it means:
   - res = number of rows affected by INSERT ... ON DUPLICATE KEY UPDATE
   - batch_size = how many rows were in this batch
   - pk = primary key field used for deduplication

   Then follows:
   Format: "Batch N: DIAGNOSTIC — pre-existing keys=X, new=Y, total_batch=Z"
   Example: "Batch 10: DIAGNOSTIC — pre-existing keys=30, new=20, total_batch=50"

   What it means:
   - pre-existing keys = rows already in table (would be UPDATEs)
   - new = rows not yet in table (would be INSERTs)
   - total_batch = should match batch_size

   Finally:
   Format: "Batch N: SUMMARY inserted={A}, updated={B}, skipped={C}, affected_rows_from_db={res}"
   Example: "Batch 10: SUMMARY inserted=20, updated=30, skipped=0, affected_rows_from_db=280"

   What it means:
   - inserted + updated should equal batch_size
   - If negative value appears here → diagnostic check failed, fallback used

───────────────────────────────────────────────────────────────────────────────

2. FETCH JOB STATUS LOGS (api_sheets_sync_routes.py):

   Level: DEBUG (while running)
   Format: "[FETCH] Job {id} status={status}, progress={N}%, message='{msg}'"
   Example: "[FETCH] Job 59429a63 status=running, progress=45%, message='Processing batch 5...'"

   Level: INFO (after completion — RED FLAG)
   Format: "[FETCH] Job {id} COMPLETE status={status}, still being polled — user_agent={ua}"
   Example: "[FETCH] Job 59429a63 COMPLETE status=done, still being polled — user_agent=Mozilla/5.0..."

   What it means:
   - If you see many "COMPLETE status=done, still being polled" entries → job completed but frontend still pinging
   - Check user_agent to find which client is polling endlessly
   - Check referer header to find which page initiated the polling

───────────────────────────────────────────────────────────────────────────────
HOW TO INVESTIGATE THE INFINITE POLLING BUG
───────────────────────────────────────────────────────────────────────────────

1. Run a full-sync or import sync from the admin dashboard

2. Watch the logs in Azure or your log aggregator for:

   a) Batch count: "Batch N: SUMMARY" entries
      Should see: batch 1, 2, 3, ... until all batches complete
      Look for: any "SUMMARY inserted=X, updated=-Y" (negative = bug triggered)

   b) Job completion: Logs should show "COMPLETE status=done" exactly once
      If it repeats 100+ times → frontend is polling forever

   c) User agent: If job is polling forever, user_agent log line shows which client
      Example: "Safari/537" or "Chrome/91" or something custom in mmr-webapp

3. Next steps:

   If you see negative updated counts:
   - Likely pre-existing row IDs have duplicates or schema mismatch
   - Run: python3 db/validate_schema.py
   - Check gmail_transactions table for duplicate MessageId values

   If job status polls forever:
   - Open browser DevTools on mmr-webapp
   - Network tab → search for "/api/sync/status"
   - Check polling interval (should stop after job.status='done')
   - Look for: infinite loop in useEffect or polling logic
   - Likely culprit: frontend not checking job.status === 'done' properly
