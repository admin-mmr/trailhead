## 1. Overview

MMR is a Chinese-American running nonprofit based in New York (~600 active members). This PRD covers the full digital infrastructure: the new Next.js 14 web application replacing the legacy Google Apps Script (GAS) system, the Azure backend, and the ongoing parallel operation of GAS during migration.

**Core goals:**
- Give members a self-service web portal to join, renew, view status, and upload payment proof
- Give volunteers a simple admin dashboard to approve payments and manage membership
- Automate payment matching (Zelle/Venmo Gmail → MySQL) to reduce manual work
- Keep Google Sheets available for ~10 volunteers who cannot use the web admin
- Support English and Chinese (中文) throughout

## 3. Authentication

### 3.1 Login Methods

The member's **email address is always the login key**. Multiple auth methods can be linked to the same account.

| Method | Status | Notes |
|---|---|---|
| **Email OTP** | ✅ Live | 6-digit code, expires 24h, sent via Azure Communication Services |
| **Password** | 🔲 Planned | bcrypt/argon2id hashed; no plaintext ever stored |
| **Google Sign-In** | 🔲 Planned | OAuth 2.0 via NextAuth.js; free, no per-call cost |
| **Microsoft Sign-In** | 🔲 Planned | Personal Outlook/Hotmail/Live; free for consumer accounts |
| **Apple Sign In** | 🔲 Planned | Required if iOS app is ever published; free per-auth |

All social login flows match the provider's email to the member's registered MMR email. First-time social login prompts the member to confirm their MMR email.

### 3.2 Session Management

- JWT session cookie, 7-day expiry, signed with `JWT_SECRET`
- `jose` library for edge-compatible JWT (Next.js middleware)
- Edge middleware protects `/portal/*` and `/api/members/*`

### 3.3 Forgot Password Flow

1. Member submits email at `/login/reset`
2. System generates a secure token, stores SHA-256 hash in `password_reset_tokens`, sends link via Azure Communication Services
3. Link expires in 1 hour, single-use
4. Member sets new password; token marked used

### 3.4 Environment Variables for Auth

```
JWT_SECRET=<64-byte base64 random>
GOOGLE_CLIENT_ID=<from Google Cloud Console>
GOOGLE_CLIENT_SECRET=<from Google Cloud Console>
MICROSOFT_CLIENT_ID=<from Azure App Registration>
MICROSOFT_CLIENT_SECRET=<from Azure App Registration>
APPLE_ID=<from Apple Developer>
APPLE_SECRET=<from Apple Developer>
```

## 4. Membership

### 4.1 Membership Types & Pricing

| Type | Annual Fee | Notes |
|---|---|---|
| Individual | $30 | One member |
| Family | $50 | Primary + family members sharing one account |
| Family Upgrade | $20 | Individual upgrading to Family mid-year |

Membership year runs April 1 – March 31.

### 4.2 Member ID Format

Sequential, format `A0001` through `A9999` (and beyond).
Generated by MySQL stored procedure `generate_member_id()` using `SELECT ... FOR UPDATE` to prevent race conditions.

> ⚠️ Note: The old brief incorrectly stated `MMR-YYYY-NNNN`. Actual production data uses `A0001` format. Do not change this.

### 4.3 Member Status

| Status | Meaning |
|---|---|
| `active` | Paid, within expiration date |
| `not active` | Expired or never activated |
| `pending` | Registered but payment not yet confirmed |

Pending state is **derived at query time** from `payment_events` — it is never stored as a status value on the member row. This is a deliberate design decision.

### 4.4 Join Flow (5 steps)

1. Member enters name, email, membership type
2. System creates member record (status: `not active`) and generates MemberID
3. Member selects Zelle or Venmo; shown QR code + payment handle + amount
4. Member submits payment confirmation: payer name, date, optional last 4 digits of transaction, optional screenshot
5. System creates `payment_events` record (status: `pending`); member sees confirmation with MemberID

### 4.5 Renewal Flow

Same as join flow but member is already logged in. Portal shows "Renew" banner when expiration is within 30 days or already past.

## 5. Payment System

### 5.1 Payment Methods

**Zelle only** and **Venmo only**. No Stripe, no credit cards, no PayPal. This eliminates transaction fees for a nonprofit.

| Method | Handle |
|---|---|
| Zelle | `treasurer@mmrunners.org` |
| Venmo | `@MMRunners` |

### 5.2 Payment Matching Pipeline

The system automatically matches incoming Zelle/Venmo payments to pending member payment events:

```
Gmail (treasurer@mmrunners.org)
    ↓  GAS scheduled trigger (every 15 min)
Google Sheet "Fetch Gmail Data" — Active tab
    ↓  Azure Function nightly sync (googleapis)
MySQL: gmail_transactions table
    ↓  Reconciliation job
payment_events: status → "Approved"
members: status → "active", Expiration updated
    ↓  Nightly export
Google Sheet "Membership Master" (read-only for volunteers)
```

**Matching rules:**
- Match on TransactionNumber (Zelle confirmation # or Venmo ID) — highest confidence
- Match on Amount + PayerName + approximate date — medium confidence
- Unmatched payments queue for admin manual review

### 5.3 Payment Event States

```
pending → matched (auto) → approved (auto or admin)
pending → rejected (admin)
pending → expired (7 days with no match)
```

### 5.4 Admin Payment Queue

Accessible at `/admin/payments`. Shows:
- All pending events (unmatched) with member info and screenshot
- All auto-matched events awaiting confirmation (medium confidence)
- Ability to manually link a Gmail transaction to a payment event
- Approve / reject with notes

- OCR attempted on upload; extracted text stored in `payment_events.OCRText`

## 8. Gmail Sync (GAS → MySQL)

### 8.1 GAS Side (already live)

- Scheduled trigger runs every 15 minutes
- Reads Gmail for Zelle notification emails and Venmo payment emails
- Parses: sender, amount, memo/note, transaction number, date, message ID
- Appends new rows to Google Sheet "Fetch Gmail Data" → Active tab
- Older rows moved to Archive tab periodically

### 8.2 MySQL Sync (planned Azure Function)

- Runs nightly (Azure Timer Function, cron `0 2 * * *` ET)
- Reads Active tab via Google Sheets API (`googleapis` npm package)
- Upserts into `gmail_transactions` table keyed on `MessageId`
- `IsArchived = false` for Active rows, `true` for Archive rows
- Triggers reconciliation job after sync

### 8.3 Reconciliation Job

- Runs after each Gmail sync
- Queries `payment_events` with status `pending` + `gmail_transactions` unmatched
- Applies matching rules (see §5.2)
- Updates `payment_events.Status`, `payment_events.MatchedMessageId`
- If approved: updates `members.Status`, `members.Expiration`, `members.MembershipFeePaid`
- Creates record in `payments` table
- Logs to `member_log`

## 15. Key Design Decisions — Do Not Reverse Without Discussion

1. **No Stripe / no credit cards** — Zelle + Venmo only. Eliminates transaction fees for nonprofit.
2. **Pending status is derived** — never stored on `members.Status`. Always query `payment_events` at display time.
3. **MemberID format is `A0001`** — sequential, generated by `generate_member_id()` stored procedure. Do not change to `MMR-YYYY-NNNN`.
4. **Email is always the login key** — true across OTP, password, and all social login providers.
5. **`next.config.mjs` not `.ts`** — Next.js 14 does not support TypeScript config. Do not rename.
6. **`postcss.config.js` must exist** — Tailwind won't compile without it.
7. **MySQL is source of truth** — Google Sheet is a downstream read-only export for volunteers.
8. **GAS Gmail trigger stays** — the scheduled Gmail → Google Sheet fetch is well-tested and stays. Only the Sheet → MySQL sync is new.
